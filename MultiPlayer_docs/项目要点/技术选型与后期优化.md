# 技术选型与后期优化

## 项目背景

当前项目是一款以**状态同步（State Synchronization）**作为网络同步方式的 MMO 类大世界游戏，使用 TCP 作为传输协议。

已实现的主要功能：
- 客户端之间的基础状态同步
- 本地客户端**预测先行（Client-Side Prediction）**
- 服务端**权威校验 + 回滚（Server Reconciliation）**
- 其他客户端**插值平滑（Entity Interpolation）**
- 基础的任务 / 背包 / 商店系统

---

## 一、技术选型

### 1. 为什么选择 TCP 而不是 UDP？

**选择 TCP 的原因**：

- **项目阶段匹配**：项目初期核心系统（任务 / 背包 / 商店）都是**低频、强可靠性**需求，项目的定位并不是偏向战斗类型，只需要同步位置、朝向以及简单的动作，对于延迟不是特别敏感，反而是对可靠性要求更高，TCP 的可靠传输天然适配这类场景。
- **开发成本低**：TCP 由操作系统内核实现可靠传输（重传、排序、流控），无需在应用层自行处理丢包重组，降低初期开发复杂度。

**TCP 的局限性（已知，后续演进方向）**：

- **队头阻塞（Head-of-Line Blocking）**：一个包丢失会阻塞后续所有包的交付，高频同步（移动 / 战斗）场景下延迟波动大。
- **Nagle 算法**：默认合并小包延迟发送，游戏场景需关闭（设置 `TCP_NODELAY`）以保证小包立即发出。
- **ACK 延迟确认**：当有响应数据时ACK确认报文会随着响应数据一起发送，如果没有就会等待响应数据。
- **拥塞控制过于保守**：TCP 的慢启动和拥塞退避机制为吞吐量优化设计，不适合游戏追求的低延迟目标。

> **演进计划**：后续引入 UDP/KCP 混合传输，将高频非关键数据（移动/朝向）走 UDP，关键数据（伤害/技能）走 KCP，保留 TCP 处理登录/交易等低频可靠场景。

### 2. 为什么选择状态同步而不是帧同步？

**状态同步 vs 帧同步对比**：

| 维度 | 状态同步 | 帧同步 |
|------|---------|--------|
| **同步内容** | 服务端计算结果（状态快照） | 玩家输入指令 |
| **计算权威** | 服务端（天然防作弊） | 各客户端独立模拟（反作弊困难） |
| **适合类型** | MMO、大世界、玩家数量多 | MOBA、格斗、RTS、玩家数量少 |
| **带宽特征** | 随同步实体数增长（需 AOI 优化） | 随玩家数增长（输入数据量小） |
| **确定性要求** | 无（服务端为准） | 严格要求浮点确定性（跨平台困难） |
| **断线重连** | 服务端直接下发当前状态，快速恢复 | 需快进重放所有历史帧，耗时长 |

**选择状态同步的核心原因**：

1. **大世界实体规模**：MMO 大世界中实体数量（NPC / 怪物 / 可交互物）远多于玩家数量，帧同步要求所有客户端模拟全部实体，计算量不可接受。
2. **服务端权威防作弊**：MMO 对数值安全要求极高（经济系统、装备、伤害），状态同步天然由服务端计算并校验，外挂只能影响表现层。
3. **AOI 天然适配**：状态同步可结合 AOI 只下发可见范围内的实体状态，帧同步则需要所有客户端拥有全局一致的世界视图。
4. **断线重连友好**：服务端直接下发最新状态快照即可恢复，帧同步需要从头回放或定期保存快照。

> **延迟补偿方案**：状态同步的固有延迟通过**客户端预测 + 服务端校验回滚 + 实体插值**三件套解决，已在项目中实现。

## 二、项目优化方向

### 1. 网络同步优化 —— AOI（Area of Interest）兴趣区域管理

**现状问题**：全量同步所有实体数据，随着玩家和实体数量增长，带宽压力急剧上升。

**优化方案**：

- **九宫格（Grid-based AOI）**：将世界划分为等大的网格，玩家只同步自身所在格子及周围相邻格子（九宫格）内的实体信息。这是 MMO 大世界中最常用、实现成本最低的方案。
- **四叉树（Quadtree）**：适用于地面为主的 2D 平面划分，递归细分空间，适合实体分布不均匀的大世界。
- **八叉树（Octree）**：在四叉树基础上增加 Y 轴划分，适用于有大量垂直空间交互的场景（如飞行、多层建筑）。对于地面为主的 MMO，四叉树或九宫格通常更合适。

> **修正说明**：原文提到"八叉树"，八叉树主要解决三维空间划分问题。对于地面行走为主的 MMO 大世界，**九宫格或四叉树**是更常见且高效的选择。八叉树适用于需要处理大量垂直空间的场景（飞行战斗、太空游戏等）。

**同步频率优化**：

AOI 解决了"同步谁"的问题，同步频率优化解决"多久同步一次、同步哪些字段"的问题：

- **差异化同步频率**：不同类型数据使用不同同步频率。移动/朝向等高频数据可 15\~20Hz 同步，属性/装备等低频数据仅在变化时同步（事件驱动）。
- **脏标记（Dirty Flag）**：每个实体维护脏标记位图，只序列化和发送本帧发生变化的字段，避免每次全量下发所有属性。
- **优先级队列（Priority Accumulator）**：根据实体与玩家的距离、重要性动态调整同步优先级。近处实体高频更新，远处实体降频甚至暂停同步，在带宽预算内最大化体验。

### 2. 传输协议优化 —— TCP + UDP/KCP 混合传输

**现状问题**：TCP 的队头阻塞和重传机制导致实时性不足，影响移动和战斗手感。

**优化方案 —— 按数据重要性分层传输**：

| 数据类型 | 推荐协议 | 原因 |
|---------|---------|------|
| 移动位置 / 朝向 / 动画状态 | **UDP（不可靠）** | 高频低价值数据，丢包可由下一帧覆盖，追求最低延迟 |
| 战斗伤害 / 技能释放 / 状态变更 | **KCP（基于 UDP 的可靠传输）** | 关键数据必须可靠送达，KCP 比 TCP 延迟更低（无队头阻塞） |
| 登录 / 交易 / 背包 / 任务 | **TCP 或 KCP** | 低频但要求绝对可靠，TCP 成熟稳定；也可统一用 KCP |

> **修正说明**：原文提到"基于 UDP 在应用层实现 ACK 重传和 SEQ 序列号"——这正是 **KCP 协议**已经实现的能力。KCP 本身就是基于 UDP 的可靠传输协议，内置了 ARQ（自动重传请求）机制，包含 ACK 确认、序列号、快速重传、选择性重传等功能，无需自行实现。直接集成 KCP 即可。

### 3. 渲染优化 —— 剔除与 LOD

**优化方案**：

- **视锥剔除（Frustum Culling）**：只渲染相机视锥体内的对象。主流引擎（Unity / Unreal）已内置，开发者需确保正确设置物体的包围盒。
- **遮挡剔除（Occlusion Culling）**：剔除被其他物体完全遮挡的对象。Unity 中需要**烘焙遮挡数据**（Window > Rendering > Occlusion Culling），Unreal 中可配置动态遮挡查询。
- **距离剔除（Distance Culling）/ LOD（Level of Detail）**：
  - 超出设定距离的对象直接不渲染。
  - 中远距离使用低精度模型（LOD 分级），减少顶点和面数。
  - 可结合 **HLOD（Hierarchical LOD）** 将远距离的多个小物体合并为一个简化网格，大幅降低 Draw Call。
- **GPU Instancing / SRP Batcher**：对大量相同材质的对象使用实例化渲染，减少 Draw Call 开销。

> **补充说明**：这些剔除技术大多是引擎内置能力，关键在于**正确配置和利用**（如 Occlusion Culling 需要烘焙、LOD Group 需要手动设置分级模型），而非从零实现。

### 4. 资源管理优化 —— AssetBundle 

**现状问题**：单场景项目暂无压力，但多场景时若资源全部常驻内存，内存占用会显著增长。

**优化方案**：

- **AssetBundle（AB 包）**：按场景 / 功能模块分包，进入场景时从磁盘异步加载，离开时卸载，降低运行时内存峰值。
- **Addressables（推荐）**：Unity 官方推荐的资源管理系统，是 AssetBundle 的上层封装，提供更友好的 API、自动依赖管理、引用计数和远程资源加载能力。新项目建议优先使用 Addressables。
- **资源预加载与过渡**：场景切换时使用 Loading 界面 + 异步加载（`LoadSceneAsync`），避免卡顿。
- **对象池（Object Pool）**：高频创建销毁的对象（特效、子弹、小怪）使用对象池复用，减少 GC 压力。

### 5. 战斗系统与大规模寻路优化

**战斗系统设计要点**：

- **技能系统**：推荐采用**数据驱动**的技能框架（如 Buff/Effect 表驱动），便于策划配置和扩展。
- **伤害计算**：服务端权威计算，客户端仅做表现预测，防止作弊。
- **状态机 / 行为树**：角色战斗状态管理可使用有限状态机（FSM）或行为树（Behavior Tree）。

**大规模敌人寻路优化**：

| 方案 | 适用场景 | 说明 |
|------|---------|------|
| **NavMesh 分块烘焙** | 大世界静态地形 | 将大地图分块烘焙 NavMesh，按需加载，避免一次烘焙整张地图 |
| **Flow Field 寻路** | 大量单位（如 RTS / 攻城战） | 为目标点生成全局流场，所有单位直接查表获取方向，适合上百个同目标单位 |
| **分帧计算（Time-Slicing）** | 通用 | 将寻路请求分散到多帧执行，避免单帧计算量过大导致卡顿 |
| **局部避障（Local Avoidance）** | 密集人群 | 使用 RVO（Reciprocal Velocity Obstacles）等算法处理单位间的碰撞避让 |
| **分层寻路（HPA*）** | 超大地图 | 先在粗粒度图上寻路确定大方向，再在局部细粒度图上精确寻路，降低计算复杂度 |

## 三、优先级建议

| 优先级 | 优化项 | 理由 |
|--------|--------|------|
| **P0（当前）** | AOI 兴趣区域管理 | 大世界 MMO 的核心瓶颈，不做 AOI 无法支撑多人同屏 |
| **P0（当前）** | UDP/KCP 混合传输 | 直接影响操作手感和战斗体验 |
| **P1（近期）** | 战斗系统框架 | 核心玩法，决定后续所有战斗相关功能的扩展性 |
| **P1（近期）** | 渲染剔除 + LOD | 多人同屏时客户端帧率保障 |
| **P2（中期）** | AssetBundle / Addressables | 多场景时才需要，单场景可暂缓 |
| **P2（中期）** | 大规模寻路优化 | 视战斗系统中敌人规模决定优先级 |
