## 模块一：状态同步要点

### 问题一：客户端如何解决无效同步请求？

**核心机制：`transform.hasChanged` 脏标记**

```csharp
// GameEntity.cs 第144-171行 — SyncRequest() 协程
IEnumerator SyncRequest()
{
    EntityState _lastState = EntityState.None;
    while (true)
    {
        // 三重条件：
        // ① IsMine — 只同步自己的角色，远程实体由服务端下发
        // ② transform.hasChanged — Unity 内置脏标记，transform 变动时自动置 true
        // ③ !actor.IsDeath — 死亡角色无需同步
        if (IsMine && transform.hasChanged && !actor.IsDeath)
        {
            // 组装同步包...
            NetClient.Send(res);

            // ★ 关键：发送后手动归零，等待下次 transform 变动
            transform.hasChanged = false;
        }
        yield return new WaitForSeconds(0.1f); // 10Hz
    }
}
```

**为什么这样做？**

| 方案 | 描述 | 问题 |
|------|------|------|
| 每 0.1s 无条件发送 | 固定频率上报 | 角色静止时发送大量冗余包，浪费带宽 |
| hasChanged 脏标记 | 只在真正移动时发送 | 静止时零网络开销 |

**`hasChanged` 的触发条件**（Unity 引擎层自动维护）：
- `transform.position` 被修改 → `hasChanged = true`
- `transform.rotation` 被修改 → `hasChanged = true`
- `transform.scale` 被修改 → `hasChanged = true`

本项目中角色移动由 `HeroController.HeroMove()` 驱动，通过 `CharacterController.Move()` 改变 `transform.position`，引擎自动将 `hasChanged` 置 `true`。

**当前实现的局限性**：
- Unity 的 `hasChanged` 在**父节点移动导致子节点被动位移时不触发** — 如果角色挂在移动平台下会漏同步
- 没有对比 Position/Rotation 的数值变化量，微小抖动（如浮点精度问题）也会触发同步

### 问题二：服务端如何做权威校验？（dt 如何计算）

**服务端校验的通用原理**（基于 MMORPG 状态同步的标准做法）：

```
客户端发送: SpaceEntitySyncRequest
    ├── Entity.Id          // 实体ID
    ├── Entity.Position    // 当前位置 (Vec3, 整数 ×1000)
    ├── Entity.Direction   // 当前朝向
    ├── Entity.Speed       // 当前速度
    └── State              // 动作状态

服务端收到后:
    ┌─────────────────────────────────────────────┐
    │ 1. 查表获取该实体上次同步时间 T_last        │
    │ 2. 计算 dt = T_now - T_last                 │
    │ 3. 理论最大位移 = Speed × dt × 系数         │
    │ 4. 实际位移 = |Pos_new - Pos_last|          │
    │ 5. if 实际位移 > 理论最大位移 + 容差:       │
    │        回滚/踢出（疑似加速挂/瞬移挂）        │
    │    else:                                    │
    │        接受 → 更新 T_last → 广播给其他客户端  │
    └─────────────────────────────────────────────┘
```

**dt 的两种计算方式**：

| 方式 | 来源 | 优缺点 |
|------|------|--------|
| **服务端时钟差** | `serverTime - lastSyncTime`（服务端自己记录） | 不受客户端影响，安全 ✓ |
| **客户端上报时间戳** | 请求中携带时间戳，服务端取差值 | 客户端可伪造时间戳 ✗ |

生产环境一定是**服务端自己记录**每个实体上次合法同步的时间戳，每次收到同步请求时用服务端当前时间减去记录的时间，得到 dt。客户端的时间戳顶多作为辅助参考（如检测客户端时钟偏移）。

**本项目服务端实际实现**（`SpaceService.cs` `_SpaceEntitySyncRequest`）：

```csharp
// 服务端代码 — 已在 SpaceService.cs 中实现
private void _SpaceEntitySyncRequest(Connection conn, SpaceEntitySyncRequest msg)
{
    var space = conn.Get<Session>().space;
    NetEntity netEntity = msg.EntitySync.Entity;
    Entity serEntity = EntityManager.Instance.GetEntity(netEntity.Id);

    // 计算位置差
    float dict = Vector3Int.Distance(netEntity.Position, serEntity.Position);
    // 使用服务器速度（而非客户端上报的速度）
    netEntity.Speed = serEntity.Speed;
    // 限制最大时间差 防止长时间挂机不动后再次移动的移动距离很长
    float dt = Math.Min(serEntity.PositionTime, 1);
    // 计算限额 = 速度 × dt × 1.5（容忍系数）
    float limit = serEntity.Speed * dt * 1.5f;

    if (float.IsNaN(dict) || limit < dict)
    {
        // 超限 → 强制拉回服务端位置
        SpaceEntitySyncResponse resp = new SpaceEntitySyncResponse();
        resp.EntitySync = new NEntitySync();
        resp.EntitySync.Entity = serEntity.EntityData;
        resp.EntitySync.Force = true;
        conn.Send(resp);
        return;
    }
    // 合法 → 广播给其他人
    space.UpdateEntity(msg.EntitySync);
}
```

**关键设计要点**：

| 要点 | 说明 |
|------|------|
| `Math.Min(PositionTime, 1)` | 限制 dt 最大为 1 秒 — 防止长时间离线后上线被误判 |
| 系数 `1.5` | 容忍 50% 的误差（网络延迟波动、客户端预测偏移） |
| 使用服务端 Speed | 忽略客户端上报的速度值，防止客户端伪造速度 |
| `Force = true` | 强制客户端立即跳转到服务端位置，不做平滑插值 |
| `PositionTime` | 服务端 Entity 每次设置 Speed 时更新 `_lastUpdate`，计算距离上次变化的时间 |

> **补充：客户端 Entity 的 `_lastUpdate` / `PositionTime` 是死代码。** 虽然客户端 [Entity.cs](d:\MyProject-Unity\MMORPG-Game\Assets\Scripts\Entities\Entity.cs) 中定义了相同的字段（第19-33行），但整个 `Assets/Scripts/` 没有任何代码引用 `PositionTime`。dt 计算完全由服务端自己的 `Entity._lastUpdate` 完成，不受客户端时钟影响。

**本项目 10Hz 同步下 dt 的典型值**：
- 正常情况：`dt ≈ 100ms`（每 0.1s 一次）
- 丢包/卡顿：`dt ≈ 200~500ms`（客户端 hasChanged 一直为 true，恢复后立即发送）
- 被攻击：`dt` 很短但位移巨大 → 触发校验 → 服务端 Force 拉回
- 长时间静止后移动：`dt` 被 cap 在 1s，按 `Speed × 1 × 1.5` 计算限额

### 问题三：客户端如何做位置预测和插值？（IsMine 分支）

**核心代码**（`GameEntity.cs` `Update()` 方法）：

```csharp
private void Update()
{
    if (!IsMine)
    {
        // === 远程实体：插值模式 ===
        // 平滑旋转到服务器方向
        var targetRotation = Quaternion.Euler(direction);
        this.transform.rotation = Quaternion.Lerp(transform.rotation, targetRotation, Time.deltaTime * 10f);
        // 平滑移动到服务器位置
        Move(Vector3.Lerp(transform.position, position, Time.deltaTime * 10f));
    }
    else
    {
        // === 本地玩家：预测模式 ===
        // 直接用本地 transform 覆盖 position（本地权威移动）
        this.position = transform.position;
        this.direction = transform.rotation.eulerAngles;
    }
}
```

**双模式对比**：

| | IsMine = true（本地玩家） | IsMine = false（远程实体） |
|---|---|---|
| **位置来源** | 本地 `transform.position`（由 HeroController 驱动） | 服务端下发的 `Vector3 position` |
| **方向来源** | 本地 `transform.rotation` | 服务端下发的 `Vector3 direction` |
| **更新方式** | 直接赋值（无延迟） | `Lerp` 插值（平滑过渡，`t = deltaTime × 10`） |
| **同步方向** | 本地 → 服务端（上报） | 服务端 → 本地（接收） |

**为什么不全部用服务端位置？**

如果本地玩家也等服务器位置回来再移动，会有 **RTT（往返延迟）** 的滞后感。本地预测让玩家操作立即生效，同时通过服务端校验兜底防止作弊。

**Lerp 系数 `deltaTime × 10` 的含义**：
- 每帧向目标位置靠近约 `10 × dt` 的比例
- 60fps 下每帧约 0.16s → `t ≈ 0.16`，约 6 帧到达
- 这是一种指数衰减式的平滑，不会突然跳变

**深入推演：Lerp 插值为什么不会无限滞后？**

直觉上"每帧只走 10%，永远追不上服务端新位置"。但关键点在于：每帧走的不是固定距离，而是**剩余差距的 10%** — 差距越大，追的距离越大；差距越小，追的距离越小。最终会达到**稳态平衡**，滞后收敛为一个常量。

> **设定**：角色速度 `v = 5 units/s`，服务端 10Hz 下发（`T = 0.1s`），客户端 60fps（`dt ≈ 0.017s`），每帧 `t = dt × 10 ≈ 0.167`。

**单周期帧级推演（100ms，6帧）**：

```
00ms:
    客户端 x=0.000 ●─────────────────────────────● 服务端目标 x=0.500
                  ◄─────── gap = 0.500 ────────►

17ms (帧1, t=0.167, 追了 0.500×0.167=0.084):
    客户端 x=0.084 ●────────────────────────● 目标 x=0.500
                  ◄───── gap = 0.416 ──────►

33ms (帧2, 追了 0.416×0.167=0.069):
    客户端 x=0.153 ●───────────────────● 目标 x=0.500
                  ◄──── gap = 0.347 ───►

50ms (帧3, 追了 0.058):
    客户端 x=0.211 ●──────────────● 目标 x=0.500
                  ◄── gap = 0.289 ─►

67ms (帧4, 追了 0.048):
    客户端 x=0.259 ●─────────● 目标 x=0.500
                  ◄ gap=0.241 ►

83ms (帧5, 追了 0.040):
    客户端 x=0.299 ●──────● 目标 x=0.500
                  ◄0.201►

100ms (帧6, 追了 0.034):
    客户端 x=0.333 ●──● 目标 x=0.500
                  ◄0.167►
    ↑ 6帧合计追上 0.333，残余 gap = 0.167

═══════════════════════════════════════════════════
  服务端新数据到达！目标从 0.500 跳到 1.000
═══════════════════════════════════════════════════

100ms:
    客户端 x=0.333 ●─────────────────────────────● 目标 x=1.000
                  ◄─────── gap = 0.667 ────────►  ← gap 重新拉大！
```

> **观察**：追的距离逐帧递减（0.084 → 0.069 → 0.034），因为 gap 越来越小。但服务端更新一到，gap 从 0.167 跳回 0.667 — **比上一轮还大**。这会无限扩大吗？不会。因为 gap 越大，下一轮的绝对追赶量也越大。


**核心结论**：`Vector3.Lerp(a, b, t)` 是指数衰减，不是线性追赶。追赶速度与剩余差距成正比 → gap 收敛于 `v×T / (1-e^(-αT))`，而非无限增长。δ ≈ 0.79 units / 158ms 对 MMO 来说完全可接受。

> **补充说明**：上述推演针对的是 **IsMine=false 的远程实体**（插值模式）。本地玩家（IsMine=true）走预测模式，`position` 直接从 `transform.position` 赋值，不经插值，确保本地操作 0 延迟响应。

### 问题四：常见的插值方案优化有哪些？（固定延迟插值缓冲 vs 当前做法）

当前项目的 `Vector3.Lerp(transform.position, position, dt*10)` 是一种**指数追赶未到达目标的朴素插值**，存在冲-停周期感、无速度预测、帧率耦合等缺陷（见上文推演）。工业界标准的做法是**固定延迟插值缓冲**，核心区别在于"追过去"还是"补过去"。

**经典范式：固定延迟插值缓冲**

```
服务端发送 (10Hz):
    S₀        S₁        S₂        S₃
    │  100ms  │  100ms  │  100ms  │
    ↓         ↓         ↓         ↓

客户端缓冲队列 (始终保留最近 N 个状态):
    [S₀, S₁, S₂]          ← 收到 S₂ 后
    [S₀, S₁, S₂, S₃]      ← 收到 S₃ 后
    [S₁, S₂, S₃]           ← S₀ 过期，丢弃

渲染 (固定延迟 L, 比如 200ms):
    t_render = now - L
            = now - 200ms

    t_render 落在 S₁ 和 S₂ 之间
    → 在 S₁ 和 S₂ 之间做插值
    → 插值因子 t = (t_render - t₁) / (t₂ - t₁)
```

**核心思想**：客户端故意比服务端慢一个固定延迟，然后在**两个已知状态之间**做确定性插值，而不是向一个未知的未来目标追逐。

**快照数据结构**：

```csharp
struct Snapshot {
    float time;      // 服务端发送时刻
    Vector3 pos;
    Vector3 vel;     // 速度（可选，用于预测）
    Quaternion rot;
}

Queue<Snapshot> buffer;  // 始终保持 ≥2 个
```

**时间驱动插值实现**：

```csharp
// 插值延迟（经验值：服务端发送间隔的 2 倍）
float INTERP_DELAY = 0.2f; // 200ms = 2×100ms

void Update() {
    float renderTime = Time.time - INTERP_DELAY;
    
    // 找 renderTime 前后的两个快照
    Snapshot from = null, to = null;
    foreach (var s in buffer) {
        if (s.time <= renderTime) from = s;
        if (s.time > renderTime) { to = s; break; }
    }
    
    if (from == null || to == null) return;
    
    // ★ 插值因子：时间比例
    float t = (renderTime - from.time) / (to.time - from.time);
    t = Mathf.Clamp01(t);
    
    // ★ 线性插值（此时是匀速的！）
    Vector3 pos = Vector3.Lerp(from.pos, to.pos, t);
    Quaternion rot = Quaternion.Slerp(from.rot, to.rot, t);
}
```

**插值因子 `t = (t_render - t₁) / (t₂ - t₁)` 图解**：

```
t₁=200ms          t_render=300ms          t₂=400ms
  │                   │                     │
  S₂                  ●                     S₃
  x=1.0              渲染点                x=2.0
  ◄─────────────────────────────────────────►
               t₂ - t₁ = 200ms
  ◄──────────────────►
    t_render - t₁ = 100ms

t = 100/200 = 0.5  →  渲染点在 S₂ 和 S₃ 正中间
pos = Lerp(S₂.pos, S₃.pos, 0.5) = 1.5
```

**三种方案数据流对比**：

```
方案 A — 固定延迟插值缓冲:
  服务端:  ═══S₀═══S₁═══S₂═══S₃═══
  缓冲:    [S₀ S₁ S₂]
  渲染:    ───────●─────────     ← 始终在 S₁ 和 S₂ 之间
  延迟=200ms                    ← 代价: 多 200ms 固有延迟
  优点: 绝对平滑，无预测错误  缺点: 延迟大，每人需缓冲

当前做法 — 纯指数追静态目标:
  服务端:  ═══S₀═══S₁═══S₂═══S₃═══
  渲染:    ───●─●─●●●───●─●─●●●  ← 冲-停-冲，周期性
  延迟≈150~200ms 但不稳定
  优点: 实现最简单           缺点: 视觉抖动，speed 闲置
```
